title: Custom scripts
description: Run your own script when discovery updates, a flow finishes, or an album request changes.
---

Aurral can run your own executable when a [notification event](/integrations/notifications/) fires, for example to tag a new album or start a media server scan.

Scripts are off by default. To turn them on, mount a folder of executable scripts and point `AURRAL_SCRIPTS_DIR` at it, then restart Aurral:

```yaml
services:
  aurral:
    environment:
      - AURRAL_SCRIPTS_DIR=/scripts
    volumes:
      - ./scripts:/scripts:ro
```

Then add scripts in **Settings > Notifications > Scripts**. Each script has its own **Events**: turn on the ones that should run it, and select **Test** to run it now. The Aurral image includes `sh`, `bash`, `python3`, `node`, and `ffmpeg`.

## What a script receives

Aurral starts the script directly, without a shell, from the scripts folder. Arguments are passed exactly as written, one per line in the settings. Event values arrive as environment variables, and as one JSON object on standard input with the keys `event`, `message`, `albumName`, `artistName`, `albumPath`, `trackName`, `path`, `username`, `userId`, `flowName`, and `flowPath`:

| Variable             | Value                                                                      |
| -------------------- | -------------------------------------------------------------------------- |
| `AURRAL_EVENT`       | The event name, for example `notifyRequestAvailable`, or `scriptTest`.     |
| `AURRAL_MESSAGE`     | A ready-made sentence describing the event, the same text Gotify receives. |
| `AURRAL_ALBUM_NAME`  | The album.                                                                 |
| `AURRAL_ARTIST_NAME` | The artist.                                                                |
| `AURRAL_ALBUM_PATH`  | The album's folder in the Library, when known.                             |
| `AURRAL_TRACK_NAME`  | The track, for **Track added**.                                            |
| `AURRAL_PATH`        | The track file, for **Track added**.                                       |
| `AURRAL_USERNAME`    | The user who requested the album or added the artist.                      |
| `AURRAL_USER_ID`     | That user's ID.                                                            |
| `AURRAL_FLOW_NAME`   | The playlist name, for **Flow finished** and **Discover updated**.         |
| `AURRAL_FLOW_PATH`   | The playlist's media path, for **Flow finished**.                          |

A variable that does not apply to the event is empty. Apart from these, a script sees only `PATH`, `HOME`, `LANG`, `LC_ALL`, `TZ`, and `TMPDIR` from Aurral's environment.

```sh
#!/bin/sh
# Log each album that becomes available.
[ "$AURRAL_EVENT" = notifyRequestAvailable ] || exit 0
echo "$(date -Is) $AURRAL_ARTIST_NAME - $AURRAL_ALBUM_NAME ($AURRAL_ALBUM_PATH)" >> /scripts/available.log
```

A script succeeds when it exits with code `0` before its timeout, which defaults to 60 seconds. When the timeout passes, Aurral stops the script and every process it started. A failed script is logged with its exit code and the end of its output, then retried, up to five attempts in all, so make running a script twice safe.

## Security

A script runs with Aurral's permissions. Only an admin can add, change, or test scripts, and Aurral runs only files inside `AURRAL_SCRIPTS_DIR`, rejecting any path that leads outside it, including through a symlink. Mount the folder read-only, as above, so nothing inside the container can change your scripts.
